## 한 줄 요약

"고치기 전에 먼저 지금 동작을 테스트로 고정한다"는 원칙으로 세 저장소를 리팩토링했고, 마지막에 **로컬 DB에 실제로 붙여 화면을 전부 눌러 보며** mock 으로는 보이지 않던 버그 12건을 더 찾아 고쳤습니다.

| 항목 | 내용 |
|---|---|
| 범위 | 서버(Express · Knex) · 관리자 웹(Next.js 14 · SWR · TanStack Table) · 참가자 웹(Next.js 14 · React Hook Form · React Query) |
| 규모 | 커밋 64건 (서버 32 · 관리자 20 · 참가자 12) · +13.1k / −14.4k 줄 (관리자는 2.4k 줄 순감) |
| 테스트 | 서버 Jest 44 · 관리자 Jest 35 · 참가자 Vitest 95 · mock E2E 172 · **실제 DB E2E 4** |
| 스택 | TypeScript · Express · Knex · PostgreSQL · Puppeteer · Next.js · SWR · React Query · Playwright · Jest/Vitest |

## 진행 방식

```
1. 특성화 테스트로 현재 동작 고정   ← 순수 함수로 추출 → 기존/새 구현 결과 비교
2. 리팩토링 · 성능 개선              ← 측정 도구를 먼저 만들고(벤치 · 렌더 카운터) 숫자로 판단
3. mock E2E 로 화면 회귀 확인        ← Playwright 172개
4. 로컬 DB 에 붙여 실제 화면 검증    ← 데모 seed + 38개 화면 순회 + 실제 DB E2E → 버그 12건 추가 발견
```

## 트러블슈팅

### 1. 저장은 됐는데 응답은 실패 — 문자 한 통이 요청 전체를 실패시켰다
- **문제** 입금 확인 → `500`. 그런데 DB 는 이미 `PAID`. 관리자는 다시 누르고("대기 상태가 아닙니다"), 참가자는 재신청하다 "이미 신청" 으로 막혔다. 리더 일정변경 승인은 문자가 **중간**에 있어 뒤의 메모 저장까지 건너뛰었다
- **대안** 문자를 트랜잭션 안에 넣기(문자 실패 시 롤백 — 하지만 문자는 되돌릴 수 없는 외부 효과) vs **커밋 뒤 문자는 실패해도 요청은 성공, 결과만 따로 알림**
- **선택 이유** 입금 확인·신청은 이미 끝난 사실이다. 실패한 것은 "알림" 뿐이다
- **해결** `notifyAfterCommit()` 으로 14곳을 감싸고, 문자 자체가 목적인 요청 3곳(입금 요청 · 리마인더)은 그대로 실패를 알림. 응답의 `messageDelivery` 를 관리자 axios 인터셉터 한 곳에서 받아 "처리는 완료됐지만 문자가 발송되지 않았습니다" 경고
- **결과** 문자 설정이 없는 로컬 서버에서도 신청 E2E 가 완료 화면까지 통과

### 2. 꼬리표 이미지에 일반 참가자가 한 명도 없었다
- **문제** 실제 데이터로 받은 꼬리표 ZIP 이 22바이트(빈 파일). 같은 데이터의 엑셀 꼬리표는 297행
- **원인** `user_type != 'STAFF'` — 일반 참가자는 `user_type` 이 `NULL` 이고, SQL 에서 `NULL != 'STAFF'` 는 참이 아니다. 새가족 · 군지체만 남았다
- **해결** 같은 저장소의 엑셀 쿼리가 이미 쓰던 `whereNull(...).orWhere(...)` 로 통일
- **배운 점** 2025년에 직접 성능을 개선했던 기능인데, mock 데이터에는 `user_type` 이 채워져 있어 몰랐다. **데이터 모양이 실제와 같아야** 찾을 수 있는 버그였다

### 3. 엑셀의 시간 · 요일이 서버 시간대에 따라 달라졌다
- **문제** 14:00 출발 버스가 엑셀에 `23:00`, 식수표 헤더가 `목저|목아…` (수요일 저녁이 목요일로)
- **원인** 9시간 더한 Date 를 `getHours()` 로 읽음 → 서버 TZ 가 한 번 더 적용. **운영(UTC)에서는 맞고 KST PC 에서는 틀린** 코드. 반대로 숙소 메모는 UTC 서버에서 아침 식사가 전날 날짜로 찍혔다
- **해결** 9시간 더한 뒤 `getUTC*` 로만 읽는 `kstParts()` 하나로 통일
- **결과** `TZ=UTC · Asia/Seoul · America/Los_Angeles` 세 환경에서 같은 결과를 내는 테스트 (이전 코드는 실패)

### 4. 리렌더 882회 → 14회 (참가자 신청 폼)
- **문제** 이름 한 글자를 칠 때마다 폼 전체(일정표 · 금액 · 모달)가 다시 그려짐. 모바일에서 입력이 끊김
- **측정** React DevTools 훅을 흉내 낸 렌더 카운터를 Playwright 에 붙여 컴포넌트별 커밋 수를 셌다 (bail-out 된 fiber 를 빼야 정확했다)
- **해결** 폼 루트의 `watch()` 를 필요한 필드만 구독하는 `useWatch` / `useFormState` 로 쪼갬
- **결과** 전화번호 13자 입력 시 렌더된 컴포넌트 882 → 14

## 기술 선택 이유

| 선택 | 이유 |
|---|---|
| 특성화 테스트 먼저 | 남이 쓴 코드를 고칠 때 "원래 이렇게 동작했다"를 테스트로 남겨야 바꾼 게 개선인지 회귀인지 판단 가능 |
| 데모 seed + 두 단계 안전장치 | 로컬 DB 터널도 `localhost` 라 host 로는 구분 불가 → 명시적 플래그 + "데모가 아닌 수양회가 있으면 중단" |
| 집계 표를 SWR 캐시 구독으로 | 서버 컴포넌트의 첫 데이터만 쓰면 테이블만 바뀐다. 같은 키를 fetcher 없이 구독해 추가 요청 없이 함께 갱신 |
| 권한 오류는 서버 판단으로 | 메뉴 데이터로 화면을 막으면 운영 DB 와 어긋날 수 있다. 조회 403 을 받으면 권한 없음 페이지로 |
| Claude Code 페어 프로그래밍 | 코드 탐색 · 반복 수정은 AI 와 함께, **무엇을 고칠지와 검증 기준(측정값 · 실제 화면 · DB 조회)은 직접 정함** |

## 회고

- **잘한 점** 숫자를 먼저 재고 고쳤다. 마지막에 실제 DB 로 화면을 눌러 본 단계에서 mock 테스트가 다 통과한 상태였는데도 12건이 더 나왔다
- **아쉬운 점** 2025년에 내가 만든 꼬리표 기능의 버그(②)를 1년 뒤에야 찾았다. 그때도 실제 데이터 모양으로 검증했어야 했다
- **다음에는** 처음부터 데모 seed 와 실제 DB E2E 를 만들어 두고 리팩토링을 시작한다
